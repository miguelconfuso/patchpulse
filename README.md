PatchPulse started with a question I had while studying graph algorithms: if BFS, Dijkstra and A* can reach the same destination, what is each one doing differently along the way?

I wanted the project to work as both software and a practical way to study search strategies. The grid shows the frontier, visited cells and final path instead of hiding the search behind a finished answer. You can draw obstacles, add weighted cells and run six algorithms under the same conditions.

## A comparison produced by the program

The table below comes from the built-in `showcase` scenario. It is generated by the same search functions used in the animation.

| Algorithm | Visited cells | Path steps | Cost | Largest frontier |
|---|---:|---:|---:|---:|
| BFS | 252 | 26 | 26 | 15 |
| DFS | 49 | 48 | 48 | 49 |
| Dijkstra | 255 | 26 | 26 | 20 |
| A* | 75 | 26 | 26 | 47 |
| Greedy Best-First | 30 | 26 | 26 | 36 |
| Bidirectional BFS | 237 | 26 | 26 | 28 |

A* reaches a path with the same cost as Dijkstra while visiting about 71% fewer cells in this scenario. Greedy visits even fewer cells, but that does not make it optimal in every grid. DFS also visits few cells here, yet the route is much longer. This is the main idea behind PatchPulse: one number is not enough to judge a search strategy.

Run the comparison yourself:

```bash
npm run benchmark
```

Add `--json` when you want the results in a format that another program can read.

## Run PatchPulse

You need Node.js 22 or newer.

```bash
git clone https://github.com/miguelconfuso/patchpulse.git
cd patchpulse
npm ci
npm run build
npm start
```

On Windows, `start.cmd` opens the project after the dependencies have been installed. The package also exposes the `patchpulse` command.

```bash
npm install -g .
patchpulse
```

Useful non-interactive commands:

```bash
npm run demo
npm run benchmark
node dist/cli.js --demo --algorithm astar --scenario weighted
node dist/cli.js --benchmark --scenario maze --json
```

## What is available in the terminal

There are five grids: `showcase`, `weighted`, `open`, `maze` and `random`. The editor supports walls, terrain with cost 7, moving the start and goal, diagonal movement and three heuristics.

| Keys | Action |
|---|---|
| Arrows or `WASD` | Move the cursor |
| `Space` | Draw with the selected tool |
| `Z` | Keep drawing while the cursor moves |
| `Tab` | Change the editing tool |
| `1` to `6` | Choose an algorithm |
| `Enter` | Start the search |
| `P`, `N`, `R` | Pause, advance one step, reset |
| `G`, `M`, `X`, `C` | Change or rebuild the grid |
| `I`, `U` | Toggle diagonals, change heuristic |
| `H`, `V`, `?` | Open theory, comparison, help |
| `Q` | Quit |

## How the search code is organised

`src/pathfinding.ts` contains the algorithms and has no dependency on the terminal interface. Its public `search()` function receives a grid and returns the visit order, path, total cost and peak frontier size. This separation lets the animation, benchmark and tests use exactly the same result.

`src/scenarios.ts` contains deterministic grids shared by the interface and command line. `src/app.tsx` handles the Ink interface and the frame-by-frame animation. `src/cli.tsx` validates arguments and decides whether to open the lab, run a demo or print a benchmark.

The weighted searches use a binary min-heap. Diagonal movement checks both adjacent corners before accepting a step, which prevents a path from passing through the corner of two blocked cells. The tests also compare A* with Dijkstra and Bidirectional BFS with BFS over seeded random grids.

## What I learned

The hardest part was not drawing the grid. It was keeping the visual explanation faithful to the algorithm. I had to separate the order of exploration from the final path, distinguish path length from path cost and test cases where a result that looks faster is not necessarily better.

Building the benchmark was especially useful because it turned the interface into something I could verify. The values in this README are not estimated screenshots. They can be reproduced from the command line.
